Gestio CRM · Infrastructure record

Sending WhatsApp through our own server

What was built on 16 July 2026, why each step was necessary, and what every piece of jargon actually means. Written to be readable without prior context.

Status: working end to end Live in: local dev only Production: still on Meta, deliberately
In one paragraph

Gestio CRM sends WhatsApp messages to parents. Until now those went through Meta, the company that owns WhatsApp reliable, but it means depending on them and paying them. Someone had started building a replacement that sends messages through our own server instead, but left it half-finished: the app code was written but switched off, and the server had no way to receive requests from the internet. We finished the server half, connected the two, and proved a real message travels the whole chain. It is switched on for development only turning it on for real parents needs a dedicated phone number first, for reasons explained at the bottom.

Part 1 The words, explained

Most of the confusion in this project comes from vocabulary rather than difficulty. Here is every term used in this document, in plain language.

Gestio CRM our product
The app in this repository. A CRM ("customer relationship management") is software for tracking the people a business deals with here, the families at a specialised centre: their files, payments and appointments. Note the repository is named dashboard-demo, which is not the product name. That mismatch caused real confusion during this work.
Meta Cloud API the old way
Meta (Facebook's parent, and WhatsApp's owner) offers an official, paid, sanctioned way for businesses to send WhatsApp messages. It is the channel Gestio CRM uses today. Because it is official, Meta will not ban you for using it as intended.
WAHA the new way
"WhatsApp HTTP API" software we run on our own server that talks to WhatsApp by pretending to be WhatsApp Web (the version you use in a browser by scanning a QR code with your phone). It is unofficial: Meta does not bless it. That is the entire trade independence from Meta, in exchange for losing Meta's protection.
n8n the glue
An automation tool. You draw a flowchart of boxes "when a request arrives, check this, then call that, then reply with this" and it runs. It sits between our app and WAHA, so the logic can change without redeploying the app.
VPS the machine
"Virtual private server" a rented computer in a data centre that is always on. Ours lives at the address 76.13.58.6 and runs Ubuntu Linux.
Docker / container packaging
A container is a program packed with everything it needs, kept in its own sealed box so it cannot interfere with its neighbours. Our server runs seven of them: n8n, WAHA, a database, a web server, and others. This causes a specific illusion that fooled us see the correction at the end.
nginx / reverse proxy the doorman
The program that answers all web traffic arriving at our server, looks at which address the visitor asked for, and forwards them to the right container behind it. A reverse proxy is exactly that: one public front door serving many private rooms.
DNS / A record the phone book
DNS turns a name people can read into an address computers use. An A record is one line in that phone book: "n8n.eiden-group.com is at 76.13.58.6". Without it, the name simply does not exist.
TLS certificate / Let's Encrypt / certbot the padlock
A certificate is what makes an address work over https rather than http the padlock in the browser. It proves the server really is who it claims and encrypts the traffic. Let's Encrypt issues them free; certbot is the tool that asks for them. They expire every 90 days and must be renewed which matters a great deal here.
Webhook the doorbell
A web address that exists to be called by another program rather than visited by a person. Our app calls n8n's webhook to say "please send this message".
Shared secret the password
A long random password that both sides know. Our app sends it with every request; n8n rejects anything without it. Necessary because the webhook is on the open internet, and without it anyone could use our server to send WhatsApp messages.
Session the linked phone
WAHA's word for one connected WhatsApp account. Creating a session and confirming it from the phone is the same act as scanning the QR for WhatsApp Web. Ours is named n8ndemo.
chatId and @c.us address format
WhatsApp does not identify people by phone number alone but by an internal id that looks like 212691422346@c.us. Note the country code is mandatory: 0691422346 is meaningless to WhatsApp; 212691422346 works.
Vercel where our app lives
The hosting service running Gestio CRM. Importantly, it is not our VPS they are different machines. This is precisely why the server needed a public address and a padlock: our app has to reach it across the open internet.
Environment variable the switch
A setting given to a program from outside its code, so behaviour can change without editing the program. N8N_WEBHOOK_URL is the switch here: when it exists, the app uses the new path; when it does not, it uses Meta. It is the whole on/off control.
SSH / RDP remote access
Two ways to use a distant computer. SSH gives a text terminal this is how the work was done. RDP gives a full graphical desktop, which is what you were using. RDP compresses the picture, and that turned out to matter.
Swap / OOM memory safety
Swap is spare disk space a machine borrows when it runs out of memory a shock absorber. Our server has none. Without it, running out of memory triggers the OOM killer ("out of memory"), which kills a program at random to survive. That is why memory was watched closely here.

Part 2 What the chain looks like

Before everything goes through Meta:

Gestio CRMon Vercel → Meta Cloud APIofficial, paid → Parent's phone

After what we built, currently used by local development only:

Gestio CRMon Vercel → nginxthe doorman → n8nthe glue → WAHAtalks to WhatsApp → Parent's phone

The app decides between the two by a single test: is N8N_WEBHOOK_URL set? If yes, the new path. If no, Meta. Nothing else changes. That design is why the work could sit finished-but-invisible for weeks the code was present and correct, but the switch was never flipped, so it behaved exactly as if nothing had been done.

Part 3 The process, and the reason for each step

  1. Read the existing notes and checked every claim

    A runbook already described this work. Rather than trust it, each statement was re-tested against the live server.

    Why: the notes turned out to be partly wrong, including one instruction that would have broken the system. Trusting them would have caused an outage.

  2. DNS created the name n8n.eiden-group.com

    Added an A record in Hostinger pointing the name at 76.13.58.6, then confirmed it resolved from three independent places.

    Why: the name did not exist at all, so nothing could reach the server by it. This blocked everything else. It required a human because the domain controls live in Hostinger's panel, with no automated access from the server.

  3. Linked a WhatsApp account to WAHA

    WAHA had zero accounts connected. The QR code could not be scanned, so a pairing code was used instead an eight-character code typed into the phone, no camera involved.

    Why the QR failed: the browser was running on the server's desktop, viewed through RDP, which compresses the image. QR codes are fine detail; compression destroys them. WhatsApp also expires each QR in 20–60 seconds and gives up after six which is exactly why the session kept dying. The pairing code sidesteps the camera entirely and worked first time.

    Why the name matters: the session was created through the API rather than the dashboard, to force the name n8ndemo. Left blank, WAHA invents a random name like session_01kxn6tr0x…, which then has to be hardcoded and changes every time the session is recreated, silently breaking everything.

  4. Freed the server's memory

    Linking WhatsApp dropped free memory to 136 MB out of 3.8 GB, with no swap. An abandoned tool called opencode was using 874 MB; stopping it restored headroom to 1.1 GB.

    Why it mattered: with no swap, the next spike would have triggered the OOM killer and it does not choose politely. It could have killed the database belonging to the other project on that machine. This was a real risk, not housekeeping.

  5. Issued a TLS certificate

    A standalone certificate for n8n.eiden-group.com, tested against a practice server first, leaving the existing certificate for the other project untouched.

    Why standalone: the safest of the options it cannot affect the other project's padlock. The alternative would have fixed more but risked more.

    Why the practice run: Let's Encrypt limits how often you may ask. A dry run proves the real attempt will succeed while writing nothing and risking nothing.

  6. Told nginx about the new address

    Added a block routing n8n.eiden-group.com to the n8n container, tested the configuration, then applied it and confirmed the other project's addresses still worked afterwards.

    Why the certificate came first: nginx refuses to start if told to use a certificate that does not exist. Doing this in the wrong order would have taken the other project offline. Order was the whole risk.

  7. Built the n8n workflow

    Four steps: receive the request → check the shared secret → call WAHA → reply. Saved into the repository as a file, so it is version-controlled rather than existing only inside n8n.

    Why secrets live outside it: the workflow reads passwords from the server's environment instead of containing them, so the file is safe to commit.

    Why the country code is added here: numbers stored as 0691422346 are converted to 212691422346 inside the workflow. One place to fix, and no need to rewrite the database.

  8. Tested it, including the ways it should fail

    Called from outside, across the public internet the same path Vercel will use:

    no secret       → 401  {"ok":false,"error":"unauthorized"}
wrong secret    → 401  {"ok":false,"error":"unauthorized"}
correct secret  → 200  {"ok":true,"waId":"3EB00F2590F79A90D4017B"}  + message arrived

    Why test the failures: proving it sends is easy. Proving it refuses strangers is what shows the door is locked and that test caught a genuine bug where nothing was being rejected at all.

  9. Switched it on for development only

    N8N_WEBHOOK_URL was added to the local .env file, and deliberately not to Vercel.

    Why not production: that one variable would route every parent's message through a personal phone number over unofficial software. See the warning below.

  10. Still to do

    Get a dedicated SIM, then switch production on. Renew both certificates before October.

Part 4 Two bugs that would never have announced themselves

Both of these produce no error. Everything looks healthy while quietly doing the wrong thing the most expensive kind of bug, and the reason the testing above was worth the time.

Bug 1 the message ID hides in a different place

WAHA reports the sent message's id as key.id. Our app looks for waId, messageId or id none of which exist in WAHA's reply. Passing WAHA's answer straight through would record every message as sent successfully with an empty id, losing the ability to trace any message ever sent. The workflow now copies key.id across explicitly.

Bug 2 a blank reply counts as success

n8n refuses to read passwords from its environment unless explicitly permitted. Without that permission it failed and returned an empty "200 OK". Our app treats a blank reply as success, because it only fails when told ok: false and blank says nothing at all. Every message would have reported success while none were sent. Fixed by permitting it (N8N_BLOCK_ENV_ACCESS_IN_NODE=false). If sending ever goes quiet, check this first.

Part 5 A correction worth recording

The runbook was wrong, and so was I

The notes claimed a stray, duplicate copy of n8n was running and wasting memory, and recommended killing it. That was investigated, agreed with, and written down as confirmed. It was false.

Containers share the machine's process list, so the n8n container appears as an ordinary program owned by the user deploy. It looked like a stray because it ran under a normal username at a normal path. Tracing its parentage settled it: 

459351  node /usr/local/bin/n8n              ← the "stray"
  └─ 459265  tini -- /docker-entrypoint.sh   ← this IS the n8n container
      └─ 459219  containerd-shim-runc-v2

Killing it would have killed n8n. It survived only because you stopped and asked what was being done before approving it. The lesson is recorded in the runbook: on this machine, check /proc/<pid>/cgroup before believing any program is running outside a container.

Part 6 Before this touches real parents

Read before switching production on

WAHA is unofficial. WhatsApp bans numbers for behaviour that looks automated and bans are driven mostly by recipients reporting or blocking you, plus machine-like patterns: bursts, identical text to many people, messaging strangers.

The risk is a gradient, not a switch. Occasional one-to-one messages to parents who know the centre and expect them are low risk. sendBroadcast the same text to the whole client list at once is the pattern that gets numbers banned.

Use a dedicated SIM you can afford to lose. Losing a personal WhatsApp account is not the same as losing this integration. Note also that a number cannot be on Meta's official API and WAHA at the same time so parents will see a different sender than they do today. That is a product decision, not just a technical one.

Changing the phone is cheap and breaks nothing: delete the session, recreate it as n8ndemo, pair the new phone. The workflow, the app and the settings all refer to the session name, never the number. That is exactly why the name was worth insisting on.

Part 7 The October deadline

Nothing renews these automatically

Certificates expire every 90 days. Automatic renewal was deliberately not set up, so this is now a diary entry:

CertificateExpiresWhat breaksWhy it won't renew
n8n.eiden-group.com 14 Oct 2026 Gestio CRM's WhatsApp sending stops Its settings are correct, but nothing is scheduled to run the renewal.
files. + ws. 12 Oct 2026 The other project (crm-edien) breaks Configured to renew by a method that cannot work here. A pre-existing fault, found by accident.

The manual renewal, which must be run before mid-October:

docker run --rm \
  -v docker_certbot-certs:/etc/letsencrypt \
  -v docker_certbot-www:/var/www/certbot \
  certbot/certbot renew --cert-name n8n.eiden-group.com \
  --webroot -w /var/www/certbot

docker exec eiden-nginx nginx -s reload   # required   renewing alone is not enough

Automating it later is a two-line scheduled job and needs no special privileges. The full detail is in docs/n8n-waha-integration.md.
